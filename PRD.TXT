# BUILD A VISUAL FINANCIAL SIMULATOR FOR SOFTWARE STARTUPS

## ROLE

You are acting simultaneously as:

* Principal Product Manager
* Technical Product Manager
* CTO
* Staff Software Engineer
* Product Designer
* UX Designer
* Simulation Engineer
* Financial Modeling Engineer
* AI Agent Architect
* Performance Engineer
* QA Engineer

You are responsible for designing and implementing a production-quality MVP of a new application.

The product is a **visual financial simulation platform for software startups**.

The core idea is:

> "Build your business model like a workflow. Connect assumptions together. Run the business forward in time. See what happens."

The product should feel closer to **n8n / React Flow / Figma** than traditional financial software.

A user who knows almost nothing about finance should be able to create a useful financial simulation.

An experienced founder or finance operator should eventually be able to build sophisticated models involving:

* revenue
* customers
* pricing
* subscriptions
* usage
* credits
* variable costs
* fixed costs
* hiring
* marketing
* CAC
* churn
* expansion
* cash
* runway
* gross margin
* contribution margin
* break-even
* scenarios
* sensitivity analysis
* Monte Carlo simulation
* capacity constraints
* operational assumptions
* probabilistic events

# 1. PRODUCT VISION

Build a product that makes financial modeling feel like building an automation workflow.

Traditional financial software:

```text
Spreadsheet
↓
Rows
↓
Columns
↓
Formulas
↓
Hard to understand
```

Our product:

```text
Input
↓
Growth
↓
Conversion
↓
Customers
↓
Pricing
↓
Revenue
↓
Costs
↓
Profit
↓
Cash
↓
Runway
```

The user should be able to visually understand how one assumption affects another.

The product must answer questions such as:

* What happens if our users grow 20% every month?
* What happens if conversion falls from 7% to 4%?
* What happens if churn increases by 2 percentage points?
* How much cash will we have in 12 months?
* When do we become profitable?
* How many customers do we need to break even?
* What happens if we hire 5 engineers?
* What happens if AI costs increase by 50%?
* How much can we spend on marketing?
* Which assumption has the biggest impact on the business?
* What is the probability that we run out of cash?
* What is our expected MRR in month 24?
* What does our downside case look like?
* What is the difference between our base, upside and downside cases?

The product should turn these questions into models and simulations.

# 2. PRODUCT PRINCIPLE

The application should follow one fundamental principle:

> NEVER HIDE THE LOGIC.

Every important output must be traceable back to its assumptions.

If the dashboard says:

```text
Month 24 MRR = $1.8M
```

the user should be able to click it and see:

```text
MRR
↓
Customers × ARPU

Customers
↓
Starting customers
+ New customers
- Churned customers
+ Expansion customers

New customers
↓
Signups × Conversion rate

Signups
↓
Starting signups × Growth rate
```

The user must always be able to answer:

> "Why did this number happen?"

# 10. CORE CONCEPTS

The simulation engine must distinguish between:

## STOCK

Something that accumulates.

Examples:

* cash
* customers
* credits
* deferred revenue
* employees

## FLOW

Something that happens during a period.

Examples:

* new customers this month
* revenue this month
* marketing spend
* credit burn

## RATE

How quickly something changes.

Examples:

* growth rate
* churn rate
* conversion rate
* cost per unit

## CAPACITY

A maximum amount that can be handled.

Examples:

* servers
* guardians
* sales capacity
* support capacity

## ASSUMPTION

A value controlled by the user.

Examples:

```text
Growth = 20%
Conversion = 7%
Price = $39
Churn = 5%
```

## OUTPUT

A calculated result.

Examples:

```text
MRR
ARR
Gross Margin
Cash
Runway
Customers
```

# 11. NODE SYSTEM

Build a generic node architecture.

Every node should have:

```typescript
type NodeDefinition = {
  id: string;
  type: NodeType;
  label: string;
  description: string;
  category: NodeCategory;

  inputs: PortDefinition[];
  outputs: PortDefinition[];

  parameters: ParameterDefinition[];

  formula?: FormulaDefinition;

  state?: StateDefinition;

  metadata?: {
    source?: "user" | "template" | "ai";
    confidence?: number;
    tags?: string[];
  };
};
```

# 19. SIMULATION ENGINE

The engine must be deterministic when given:

```text
model
parameters
seed
```

Same inputs + same seed must produce the same output.

This is essential for debugging and reproducibility.

Simulation:

```text
initialize state

for each timestep:

    resolve inputs

    resolve flows

    resolve formulas

    update stocks

    apply conditions

    calculate financial statements

    calculate metrics

    record state
```

Do not tie the simulation engine to React.

The simulation engine must be pure TypeScript.

It must be runnable:

* in browser
* server-side
* tests
* CLI
* Web Worker

# 43. CIRCULAR DEPENDENCIES

The model engine must detect:


# 106. FINAL QUALITY BAR

Before declaring the product complete, verify:

### UX

* Can a non-finance user build a model?
* Is every important concept understandable?
* Can users understand why a number changed?
* Are errors understandable?

### Simulation

* Are calculations deterministic?
* Are units consistent?
* Are circular dependencies detected?
* Are Monte Carlo results reproducible?
* Can every metric be traced to inputs?

### AI

* Does AI create valid graph JSON?
* Does AI use tools?
* Does AI ask when assumptions are missing?
* Does AI avoid inventing financial outputs?
* Does Ollama work locally?

### Performance

* Does the canvas remain smooth?
* Does Monte Carlo avoid freezing the UI?
* Is the initial bundle small?
* Are charts lazy-loaded?
* Can the app run comfortably on Vercel Hobby?

### Trust

* Are actuals, assumptions, forecasts and simulations clearly distinguished?
* Does every AI assumption have a source?
* Can users inspect formulas?
* Can simulations be reproduced?

If any of these fail, do not consider the MVP finished.
